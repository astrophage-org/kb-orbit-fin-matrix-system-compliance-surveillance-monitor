# Trade Matched Event Entity

The `TradeMatchedEvent` is a strongly-typed Pydantic data model representing a execution/match transaction emitted by the core exchange matching engine. In the [[summaries/project-astrophage]] architecture, this entity serves as the canonical structured payload for all matched-trade analysis, specifically fueling the wash-trade graph builder and the compliance rules engines.

---

## 1. Class Definition

Defined in `src/consumers/schemas.py`, the model uses Pydantic to enforce data-type validation and constraints at the stream edge before payloads enter downstream analytical detectors.

```python
from pydantic import BaseModel, Field

class TradeMatchedEvent(BaseModel):
    trade_id: str = Field(..., description="Unique identifier for the trade")
    buyer_id: str = Field(..., description="ID of the buyer")
    seller_id: str = Field(..., description="ID of the seller")
    instrument: str = Field(..., description="Symbol of the traded instrument")
    price: float = Field(..., description="Execution price")
    quantity: float = Field(..., description="Execution quantity")
    timestamp: int = Field(..., description="Epoch timestamp of match")
```

---

## ## Responsibilities

The `TradeMatchedEvent` entity carries the following architectural and operational responsibilities:

* **Inbound Validation & Type Safety**: Parses raw, unstructured JSON messages from the `nte.trades.matched` Kafka topic, ensuring that invalid, malformed, or missing trade attributes are caught immediately at the consumer boundary.
* **Graph Input Representation**: Serves as the primary transaction schema passed to the [[concepts/wash-trade-detection]] engine (`WashTradeDetector`) to map graph edges ($Seller \to Buyer$) within active sliding windows.
* **AML Verification Target**: Provides standardized identifier properties (`buyer_id`, `seller_id`) utilized by the [[concepts/rules-engine-aml]] to verify entity state against active OFAC lists and sanction configurations in [[entities/aml-config]].
* **Decoupled Serialization**: Supports clean schema serialization and deserialization across the microservice boundary, ensuring strict conformity to the architecture specified in [[decisions/decoupling-analytics-transport]].

---

## ## Dependencies

The `TradeMatchedEvent` sits at the boundary of ingestion and analytics, interacting with multiple platform systems:

### Upstream Dependencies
* **Kafka Message Broker**: Receives real-time streaming JSON entries from the `nte.trades.matched` topic published by the **Order Matching Engine**.
* **Pydantic Framework**: Utilizes `pydantic.BaseModel` and `pydantic.Field` for parsing, validation, and serialization.

### Downstream Dependencies
* **[[concepts/surveillance-stream-processor]]**: The main Spark/Kafka ingestion loop utilizes this schema to unpack batch records prior to classification.
* **[[concepts/wash-trade-detection]]**: The cycle detection graph uses the fields `buyer_id`, `seller_id`, `instrument`, and `quantity` to formulate directed multi-graphs.
* **[[concepts/rules-engine-aml]]**: The declarative rules engine uses this entity to execute static watchlist checks (e.g., Rule `AML_002` - Sanctioned Entity Interaction).
* **[[decisions/decoupled-persistence]]**: Parsed and processed event records are ultimately structured according to this schema when written to BigQuery `gfmg_surveillance.alerts_log` for regulatory archival.

## 2. Field Specifications & Constraints

| Field Name | Data Type | Constraints / Description |
| :--- | :--- | :--- |
| `trade_id` | `str` | Must be a unique, non-empty identifier generated by the matching engine. |
| `buyer_id` | `str` | The unique identifier of the purchasing counterparty. |
| `seller_id` | `str` | The unique identifier of the selling counterparty. |
| `instrument`| `str` | Financial ticker symbol or product ID (e.g., `AAPL`, `BTCUSD`). |
| `price` | `float` | Non-negative trade execution price. |
| `quantity` | `float` | Non-negative executed order size. |
| `timestamp`| `int` | Unix epoch timestamp (milliseconds or seconds precision depending on engine configuration). |

## 3. Example Payloads

### Valid Serialization Map
The following JSON payload represents a typical event conforming to the `TradeMatchedEvent` model:

```json
{
  "trade_id": "TX-9908234-A",
  "buyer_id": "TraderA",
  "seller_id": "TraderB",
  "instrument": "AAPL",
  "price": 150.50,
  "quantity": 100.0,
  "timestamp": 1692230400
}
```

### Invalid Payload Handling
If the incoming Kafka event possesses a negative quantity or fails to supply a crucial field (like `buyer_id`), the `SurveillanceStreamProcessor` discards the malformed payload at the ingestion boundary, logging a Pydantic `ValidationError`. This prevents invalid floating-point errors or downstream `NoneType` issues within the `NetworkX` graph traversal code used by [[concepts/wash-trade-detection]].
